# Обновление безопасности зависимостей frontend

23.10.2026 Next.js и связанные зависимости обновлены в feature-ветке.
Полный `npm audit` после чистой установки сообщает **0 известных уязвимостей**.
Это результат проверки npm-графа на указанную дату, а не гарантия отсутствия
неизвестных ошибок или аудит внешнего окружения.

## Версии

| Зависимость | До | После |
| --- | --- | --- |
| Next.js | 16.4.0 | 16.4.3 |
| eslint-config-next | 16.4.0 | 16.4.3 |
| React / React DOM | 19.3.0 | 19.3.1 |
| Vitest | 3.2.7 | 4.1.12 |

Версии прямых обновлённых зависимостей зафиксированы в `package.json`, полный
граф — в `package-lock.json`. Изменения прикладного кода и настроек защиты
не потребовались. Уведомления Next.js об обновлениях безопасности не отключались.

## Основание

[Официальное сообщение Next.js от 14.10.2026](https://nextjs.org/blog/nextjs-security-update-october-14-2026)
описывает исправления выполнения кода в Cache Components и обработке SVG,
а также отказа в обслуживании через Server Actions. Версия 16.4.0 входит
в затронутый диапазон; исправления выпущены начиная с 16.4.1.
Для проекта выбрана доступная стабильная 16.4.3 в той же ветке 16.4.

До обновления полный npm audit отмечал четыре уязвимых пакета: `next`, `vitest`,
`@vitest/mocker`, `tinypool`. Поэтому обновлён также тестовый runner:
Vitest 4.1.12 использует исправленный mocker и не требует прежний tinypool.
Примеры обнаруженных advisories:
[mocker](https://github.com/advisories/GHSA-qxg6-89mg-rqv8),
[tinypool](https://github.com/advisories/GHSA-85c8-ppgw-ccpr).
Аудит выполнен со всеми зависимостями, без исключения devDependencies.

## Проверки

- Чистая установка `npm ci` по обновлённому lock-файлу прошла.
- Полный `npm audit`: 0 уязвимостей всех уровней.
- 32 frontend-теста (11 API/прокси и 21 UI), lint и production-сборка прошли.
- Сборка Next.js 16.4.3 больше не выдаёт предупреждение об уязвимой версии.
- 164 backend-теста прошли без пропусков, включая 21 интеграционный с настоящим TLC.
- В браузере с production frontend, FastAPI и FakeLLMProvider проверены оба
  acceptance-сценария с настоящим TLC: `PROPERTY_VIOLATED` с четырьмя состояниями
  и `PROPERTY_HOLDS` после явного сброса approved. Повторный анализ и HTTP 422
  без старого результата работают.

FakeLLMProvider в этой браузерной проверке задаёт фиксированные модель и
объяснение; формальную проверку выполняет настоящий TLC. Контракты МАИ,
достижимость и ссылки на требования дополнительно покрыты backend-тестами.
Деплой и обновление `main` в эту задачу не входят: результат публикуется в `develop`.
