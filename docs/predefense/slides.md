# Презентация первой предзащиты

## 1. Команда и тема проекта

**Содержимое слайда:**

- ИИ-агент-аналитик для проверки логики требований.
- Команда it plow, учебный проект МАИ.
- Попков Максим Александрович — тимлид.
- Орловский Андрей Максимович — Frontend; Кузьмин Никита Александрович — Backend.

**Визуал:** название проекта, состав команды и цепочка «текст → модель → проверка → объяснение».

**Заметки докладчика:** Мы разрабатываем систему, которая помогает проверить последствия правил, описанных обычным текстом. На первой предзащите представляем требования, архитектуру и технический прототип.

## 2. Проблема и назначение системы

**Содержимое слайда:**

- Текст требований может допускать нежелательную последовательность действий.
- Правдоподобная интерпретация ещё не подтверждает логическую согласованность.
- Пользователь задаёт поведение модуля обычным текстом.
- Система возвращает модель, результат проверки и понятное объяснение.

**Визуал:** требование о заявке и путь «согласована → отменена → исполнена» с выделенным последним переходом.

**Заметки докладчика:** Например, отмена заявки может не сбрасывать признак согласования. Если исполнение проверяет только этот признак, отменённую заявку всё ещё можно исполнить. Мы хотим находить такие сценарии до реализации модуля.

## 3. Требования к системе

**Содержимое слайда:**

- Выделить переменные состояния, события, guards, effects и свойства.
- Построить модель и передать её детерминированному движку.
- Получить статус и контрпример при нарушении.
- Объяснить результат без автоматического исправления модели.
- Поддержать `invariant`, `forbidden_state`, `reachable`, `deadlock_free`; первые два уже реализованы.

**Визуал:** этапы «формализация → проверка → контрпример → объяснение» и четыре типа свойств с отметками готовности.

**Заметки докладчика:** Главный результат — понятный бизнес-сценарий, найденный машинной проверкой. Для первого прототипа мы реализовали проверку инвариантов и запрещённых состояний. Достижимость и отсутствие блокировок остаются следующими задачами.

## 4. Главная архитектурная идея

**Содержимое слайда:**

- LLM интерпретирует требования и формирует модель со свойствами.
- Model Checker проверяет последствия заданных правил.
- `BehavioralModel` служит границей между двумя частями.
- Перебор состояний и формальный результат принадлежат TLC.
- Соответствие модели смыслу требований оценивается отдельно.

**Визуал:** блоки «Вероятностная интерпретация» и «Детерминированная проверка», между ними модель, в обратную сторону — результат.

**Заметки докладчика:** Мы разделили работу со смыслом и формальную проверку. TLC позволяет проверить последствия конкретной интерпретации, но не определяет, правильно ли LLM поняла исходный текст. Поэтому модель и контрпример доступны пользователю вместе с объяснением.

## 5. Архитектура системы

**Содержимое слайда:**

- Frontend на Next.js обращается к FastAPI через серверный маршрут `/api/analyze`.
- Analyst Agent использует интерфейс `LLMProvider`.
- OpenRouter строит модель и объяснение; fake возвращает фиксированный пример.
- Model Checker: Validator → TLA+ Generator → TLC Runner → Result Parser.
- `VerificationResult` отделён от текста объяснения.

**Визуал:** [схема компонентов](architecture.md) с отдельными областями LLM и Model Checker; между Frontend и FastAPI показан серверный маршрут Next.js.

**Заметки докладчика:** Backend выполняет один последовательный запрос и запускает TLC отдельным Java-процессом. Оба провайдера работают через общий интерфейс. Fake заменяет построение модели и объяснение, а формальная проверка остаётся той же. Frontend уже подключён к API и показывает реальные результаты проверки.

## 6. Как проходит проверка требования

**Содержимое слайда:**

- FastAPI принимает текст требований.
- Провайдер строит BehavioralModel, Validator проверяет её допустимость.
- Генератор создаёт TLA+, TLC исследует достижимые состояния.
- Парсер возвращает статус, трассу и статистику.
- Второй вызов провайдера объясняет результат пользователю.

**Визуал:** пять шагов обработки запроса на основе [диаграммы взаимодействий](sequence.md).

**Заметки докладчика:** Невалидная модель отклоняется до запуска движка. Если TLC не завершает проверку, система возвращает отдельный статус. Объяснение строится на результате Model Checker и не должно заменять его собственным выводом LLM.

## 7. Пример counterexample

**Содержимое слайда:**

- `Approve` устанавливает `approved=true`.
- `Cancel` устанавливает `cancelled=true`, сохраняя `approved`.
- `Execute` разрешён при `approved=true`.
- TLC находит `Created → Approved → Cancelled → Executed`: `PROPERTY_VIOLATED`.
- Сброс `approved=false` в `Cancel` даёт `PROPERTY_HOLDS` для того же свойства.

**Визуал:** четыре состояния с признаками `approved` и `cancelled`; выделены сохранённое разрешение после отмены и итоговое нарушение.

**Заметки докладчика:** Контрпример показывает допустимую последовательность именно в построенной модели. Причиной может быть ошибка требований или их интерпретации. В исправленном примере мы явно меняем одно правило и повторяем проверку того же свойства.

## 8. Что уже реализовано

**Содержимое слайда:**

- FastAPI, Analyst Agent и полный конвейер Model Checker.
- Реальный TLC подтверждает оба acceptance-сценария.
- Проходят 78 тестов backend, включая четыре интеграционных теста с TLC, и 11 тестов frontend; lint и сборка проходят.
- FakeLLMProvider обеспечивает воспроизводимый сквозной сценарий.
- OpenRouter интегрирован; ответы внешних моделей проходят валидацию BehavioralModel.

**Визуал:** компоненты прототипа и два результата: `PROPERTY_VIOLATED` с трассой и `PROPERTY_HOLDS` после правки.

**Заметки докладчика:** Мы проверили сценарий через API и настоящий TLC. Интеграция с OpenRouter также реализована, но ответы бесплатных внешних моделей могут не соответствовать схеме. Валидация отсеивает такие ответы до проверки. Автотесты провайдера используют подмену HTTP, поэтому стабильность внешней модели оценивается отдельно.

## 9. Следующие шаги

**Содержимое слайда:**

- Оценить соответствие модели исходным требованиям на новых предметных сценариях.
- Подключить предоставленный API LLM МАИ через `LLMProvider` (#20), затем оценить качество формализации на нём (#13). OpenRouter сохраняется как альтернатива; API МАИ пока не реализован.
- Реализовать `reachable` и `deadlock_free` с учётом допустимых конечных состояний.
- Добавить привязку к требованиям и уточнение интерпретации.
- Улучшить обработку ошибок LLM и возврат результата TLC при сбое объяснения.
- Расширить сценарии проверки интерфейса и поддержку ошибок внешней LLM.

**Визуал:** три направления развития: свойства модели, качество интерпретации, интеграция интерфейса.

**Заметки докладчика:** Прототип уже позволяет проверить архитектурную идею на контрольном примере. Дальше расширяем поддерживаемые свойства и делаем пользовательский сценарий устойчивее, сохраняя разделение LLM и детерминированного ядра.
