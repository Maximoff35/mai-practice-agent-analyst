# Сквозная демонстрация MVP

Запустите backend и frontend по [общей инструкции](../../README.md).
Для воспроизводимой предзащиты задайте backend `LLM_PROVIDER=fake`.
Это демонстрационный провайдер модели и объяснения; проверяет модель настоящий TLC.

## Нарушение свойства

В интерфейсе нажмите «Подставить пример». Текст:

> Заявка имеет статус Created, Approved, Cancelled или Executed и признаки approved и cancelled. Изначально статус Created, оба признака false. Approve разрешён только в Created и задаёт Approved и approved=true. Cancel разрешён в Created или Approved и задаёт Cancelled и cancelled=true, не меняя approved. Execute разрешён при approved=true независимо от статуса и задаёт Executed. Запрещено состояние status=Executed при cancelled=true. Проверь именно эти правила без исправлений.

Это полный acceptance исходного кейса с явно ошибочными guards/effects.
Короткая фраза «Заявка после согласования может быть исполнена. Пользователь
может отменить заявку до исполнения» не задаёт initial, точные guards/effects
и сохранение approved после отмены. Для неё не требуйте от LLM выдумывать
ошибку: покажите выбранные свойства, предположения и вопросы над вкладками.
Даже общий `PROPERTY_HOLDS` может относиться лишь к достижимости, а не запрету.

После анализа покажите модель: `Cancel` не сбрасывает `approved`, а `Execute`
проверяет только `approved=true`. Свойство запрещает сочетание
`status=Executed AND cancelled=true`.

Ожидаются `PROPERTY_VIOLATED` и контрпример:

| Шаг | Переход | status | approved | cancelled |
| --- | --- | --- | --- | --- |
| 1 | Начальное состояние | Created | false | false |
| 2 | Approve | Approved | true | false |
| 3 | Cancel | Cancelled | true | true |
| 4 | Execute | Executed | true | true |

Объяснение связывает нарушение с сохранённым разрешением после отмены.
Это вывод о построенной модели; неверная интерпретация требований тоже
может быть причиной нарушения.

## Явное исправление

Нажмите «Уточнить требования и проверить снова» и замените в правиле Cancel
`не меняя approved` на:

> сбрасывая approved=false

Повторный анализ должен вернуть `PROPERTY_HOLDS`, показать новый эффект
в `Cancel` и отсутствие контрпримера. Агент не исправляет модель автоматически.

## Ошибки

- Пустой текст: кнопка анализа недоступна.
- В режиме `fake` введите «Проверить движение лифта»: backend вернёт 422,
  интерфейс покажет ограничение демонстрационного провайдера без старого результата.
- Остановите backend и повторите анализ: интерфейс покажет ошибку доступности,
  а не подставной контрпример. После запуска backend анализ можно повторить.
- `TIMEOUT` и `STATE_LIMIT_REACHED` не считаются успешной проверкой.

## Разделение компонентов

Браузер → Next.js `/api/analyze` → FastAPI → Analyst Agent → BehavioralModel →
Validator → TLA+ → Java/SANY → Java/TLC → результат и трасса → объяснение → интерфейс.
Next.js только пересылает JSON; Model Checker не использует LLM.
Ключи провайдера остаются на backend, адрес FastAPI задаётся серверной
переменной `BACKEND_URL`. Для свободного текста используйте МАИ или OpenRouter,
учитывая возможные ошибки внешнего API и формализации.

## Предположения и повторная проверка

В режиме МАИ введите короткий пример выше, затем пример с отсутствующим initial:
«Булева переменная ready. Prepare разрешён при ready=false и задаёт ready=true.
Проверь достижимость ready=true. Начальное значение не задано».
Покажите `interpretation.assumptions`, `questions` и обоснования свойств.
Если провайдер не передал метаданные, интерфейс прямо предупреждает об этом;
отсутствие вопросов не доказывает полноту требований.
Через кнопку уточнения добавьте «Изначально ready=false» и запустите повторно.
Пока текст редактируется, старый результат подписан как предыдущий; при новом
запросе он очищается. Модель автоматически не исправляется.

Реальные ответы и ограничения: [проверка 7 ноября](../reliability-evaluation.md).
