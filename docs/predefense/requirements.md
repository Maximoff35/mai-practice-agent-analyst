# Требования к системе

## Назначение

Система помогает проверить логику требований к поведению информационного модуля. Analyst Agent преобразует текст в формальную модель, Model Checker проверяет её свойства, а агент объясняет результат на языке пользователя.

Проверка должна выявлять неочевидные допустимые последовательности событий. Например, отмена заявки может сохранять признак согласования, из-за чего исполнение остаётся разрешённым.

## Вход и выход

Пользователь описывает поведение системы обычным текстом и получает результат анализа.

| Граница | Данные |
| --- | --- |
| Пользователь → Analyst Agent | Текстовое описание поведения модуля |
| Analyst Agent → Model Checker | Переменные состояния с конечными доменами, начальное состояние, переходы с guards/effects и проверяемые свойства |
| Model Checker → Analyst Agent | Статус, статистика проверки; при нарушении — контрпример с состояниями и названиями переходов |
| Analyst Agent → пользователь | Понятное объяснение результата, сценарий нарушения и гипотеза о его причине |

Для связи результата с исходным текстом желательно поддержать ссылки элементов модели на требования и поле `related_requirements`.

## Обязанности Analyst Agent

1. Определить объект анализа, сущности и участников.
2. Выделить переменные состояния и начальное состояние.
3. Определить события, переходы, условия выполнения и изменения состояния.
4. Сформулировать проверяемые свойства и построить структурированную модель.
5. Передать модель в Model Checker и получить результат.
6. Объяснить контрпример на языке требований.
7. Предложить гипотезу о причине нарушения и при необходимости задать уточняющий вопрос.

Агент не должен молча исправлять модель: причиной контрпримера может быть ошибка в требованиях, неверная интерпретация или пропущенное правило.

## Обязанности Model Checker

| Этап | Требование |
| --- | --- |
| Валидация | Проверить уникальность имён переменных и переходов, типы, начальные значения, принадлежность доменам, ссылки на переменные, guards, effects и свойства |
| Компиляция | Преобразовать ограниченный DSL проекта в TLA+ и конфигурацию TLC |
| Запуск | Запустить TLC отдельным subprocess с контролем времени и принудительным завершением при timeout |
| Проверка | Передать TLC перебор достижимых состояний и проверку свойств |
| Результат | Вернуть структурированный статус; при нарушении — путь от начального состояния до первого нарушения с названиями переходов |

Model Checker работает детерминированно и не использует LLM. Самостоятельный перебор состояний агентом не допускается; алгоритм model checking выполняет TLC.

## Свойства

| Тип | Смысл |
| --- | --- |
| `invariant` | Утверждение истинно во всех достижимых состояниях |
| `forbidden_state` | Состояние, описанное выражением, недостижимо |
| `reachable` | Существует хотя бы один допустимый путь к целевому состоянию |
| `deadlock_free` | Нет достижимых состояний, из которых не разрешён ни один дальнейший переход |

## Статусы результата

| Статус | Значение |
| --- | --- |
| `PROPERTY_HOLDS` | Свойство не нарушено в проверенной конечной модели при заданных ограничениях |
| `PROPERTY_VIOLATED` | Найден допустимый путь, нарушающий свойство модели |
| `MODEL_INVALID` | Модель некорректна |
| `TIMEOUT` | Проверка не завершена за отведённое время |
| `STATE_LIMIT_REACHED` | Достигнут предел числа состояний; проверка не завершена |
| `ENGINE_ERROR` | Ошибка движка или его запуска |

`TIMEOUT` и `STATE_LIMIT_REACHED` нельзя трактовать как `PROPERTY_HOLDS`. Объяснение агента должно сохранять смысл статуса, полученного от Model Checker.

## Ограничения

Модель должна быть конечной. Переменные имеют тип `enum`, `boolean` или `integer` с границами `min/max`. Переход задаётся именем, условием выполнения и эффектами. Поддержка произвольного TLA+ не требуется: используется ограниченный DSL проекта.

Проверяется формализованная интерпретация требований и выбранные свойства. `PROPERTY_VIOLATED` может указывать как на проблему в требованиях, так и на ошибку интерпретации агентом. `PROPERTY_HOLDS` не является доказательством корректности production-системы.

## Acceptance-сценарии

Начальное состояние обоих сценариев: `status=Created`, `approved=false`, `cancelled=false`.

### Обнаружение нарушения

- `Approve` разрешён в `Created` и устанавливает `status=Approved`, `approved=true`.
- `Cancel` разрешён в `Created` или `Approved` и устанавливает `status=Cancelled`, `cancelled=true`, сохраняя `approved`.
- `Execute` разрешён при `approved=true` и устанавливает `status=Executed`.
- Запрещена комбинация `status=Executed AND cancelled=true`.

Ожидаемый результат — `PROPERTY_VIOLATED` и контрпример:

```text
Created → Approve → Approved → Cancel → Cancelled → Execute → Executed
```

### Исправленная модель

В `Cancel` явно добавляется эффект `approved=false`. Остальные правила и проверяемое свойство сохраняются.

Ожидаемый результат — `PROPERTY_HOLDS`. Исправление задаёт пользователь; агент не изменяет модель автоматически после обнаружения нарушения.

## Критерий качества и тестирование

Система должна строить явную модель из неформального текста, формулировать свойство, запускать детерминированную проверку и объяснять найденную последовательность как понятный бизнес-сценарий.

Проверки охватывают три уровня:

- unit-тесты валидации, компиляции выражений и моделей, разбора трасс;
- integration-тесты `BehavioralModel → TLC → результат`;
- тесты агента `текст → модель → проверка → объяснение`.

## Ограничения текущего прототипа

Реализованы `invariant` и `forbidden_state`. Поддержка `reachable`, `deadlock_free`, ссылок на исходные требования и отдельного диалога уточнений остаётся дальнейшей работой. Статус `STATE_LIMIT_REACHED` распознаётся, но настройка лимита состояний пока не поддерживается.

Текущие интерфейсы описаны в [архитектуре системы](architecture.md), результаты проверок — в [описании прототипа](prototype.md).
