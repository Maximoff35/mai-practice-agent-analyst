# Текущий прототип

Прототип объединяет анализ требований, построение конечной модели, проверку через TLC и объяснение результата. Для воспроизводимых сценариев используется FakeLLMProvider, для работы с внешней LLM — MAIProvider или OpenRouterProvider.

API LLM МАИ (`https://api-ai.mai.ru/`) подключён через существующий `LLMProvider`. Контрольные прогоны 16.10.2026 и выбор `qwen3.6-35b-a3b` описаны в [отчёте оценки](../llm-quality.md); [план проекта](../roadmap.md) сохраняет следующие этапы.

## Что реализовано

| Компонент | Возможности |
| --- | --- |
| Frontend / Next.js | Ввод требований, подключение FastAPI через серверный прокси, модель, свойства, результат, трасса и объяснение |
| FastAPI | Приём требований через `/api/analyze`, структурированный ответ, `/health` |
| Analyst Agent | Последовательность «построение модели → проверка → объяснение» через интерфейс `LLMProvider` |
| BehavioralModel и Validator | Pydantic-схемы, проверка типов, конечных доменов, ссылок, выражений и переходов |
| TLA+ Generator | Компиляция ограниченного DSL, генерация `.tla/.cfg`, сохранение неизменённых переменных |
| TLC Runner | Запуск настоящего TLC отдельным Java-процессом, контроль timeout |
| Result Parser | Статусы, статистика, контрпример и названия переходов |
| FakeLLMProvider | Ошибочный и исправленный варианты модели заявки, шаблонные объяснения без сети |
| MAIProvider | API МАИ по официальному OpenAPI, конфигурация, валидация модели, безопасные ошибки |
| OpenRouterProvider | HTTPS-запросы для построения модели и объяснения, валидация ответа |

Интеграция с OpenRouter реализована, однако ответы бесплатных внешних моделей могут не всегда соответствовать схеме BehavioralModel, поэтому перед проверкой выполняется валидация. Невалидный ответ отклоняется до запуска TLC. Соответствие модели смыслу требований оценивается отдельно от её формальной корректности.

## Acceptance №1 — обнаружение нарушения

[Ошибочная модель](../../backend/tests/fixtures/buggy_model.json) проверяет свойство `NoExecutedAfterCancel` типа `forbidden_state`: комбинация `status=Executed AND cancelled=true` недопустима.

TLC возвращает `PROPERTY_VIOLATED`. Контрпример содержит четыре состояния:

| Номер | Переход | `status` | `approved` | `cancelled` |
| --- | --- | --- | --- | --- |
| 1 | — | Created | false | false |
| 2 | Approve | Approved | true | false |
| 3 | Cancel | Cancelled | true | true |
| 4 | Execute | Executed | true | true |

После отмены `approved` остаётся истинным. Guard перехода `Execute` проверяет только этот признак, поэтому отменённая заявка может быть исполнена. Интеграционный тест проверяет статус, состояния и названия переходов.

## Acceptance №2 — исправленная модель

В [исправленной модели](../../backend/tests/fixtures/fixed_model.json) переход `Cancel` дополнен эффектом `{"set": ["approved", false]}`. Остальные правила и проверяемое свойство сохраняются.

TLC возвращает `PROPERTY_HOLDS`: после отмены guard `Execute` становится ложным. Исправление задаётся явно; агент не редактирует модель автоматически по результатам проверки.

## Интерпретация результата

Model Checker проверяет формализованную модель и свойства, сформированные на основании интерпретации требований. `PROPERTY_VIOLATED` не означает автоматически, что исходные требования или production-система ошибочны. Причиной могут быть неверная интерпретация агента, слишком сильное свойство или пропущенное правило.

`PROPERTY_HOLDS` подтверждает выбранные свойства конечной модели при заданных ограничениях. Он не подтверждает свойства, которые не проверялись, и не доказывает корректность production-системы.

## Ограничения текущей версии

- Поддерживаются `invariant`, `forbidden_state`, `reachable`; `deadlock_free` требует реализации. Путь к цели отображается отдельно от контрпримера.
- FakeLLMProvider работает только с фиксированным сценарием заявки и отмены.
- Воспроизводимая демонстрация использует fake-провайдер модели и объяснения; произвольный текст требует МАИ или OpenRouter и проверки интерпретации. Сам frontend использует настоящий API.
- Ссылки на исходный текст необязательны. Для подтверждения используется маркер
  `[REQ-1]` и точное поле `fragment`; неподтверждённые ссылки отклоняются.
  Отдельный диалог подтверждения модели пока не поддерживается.
- Статус `STATE_LIMIT_REACHED` распознаётся, но управляемый лимит состояний не задан. Разбор TLA+ выполняется при запуске TLC без отдельного вызова SANY.
- Парсер зависит от текстового формата TLC; название перехода может остаться неопределённым при неоднозначности.
- Повторные LLM-запросы и переключение провайдера выполняются вручную. При ошибке объяснения API сохраняет модель и результат TLC с явно помеченным шаблонным сообщением.
- Семантическая точность модели и объяснения автоматически не оценивается.

Контракты компонентов и обработка ошибок описаны в [архитектуре системы](architecture.md).
