# Контракт свойств и результатов проверки

`reachable` проверяет существование хотя бы одного допустимого пути к состоянию,
в котором истинно `expression`. Начальное состояние тоже входит в поиск.
Интерпретация результата отличается от инварианта:

| Тип | `PROPERTY_HOLDS` | `PROPERTY_VIOLATED` | Путь |
| --- | --- | --- | --- |
| `invariant` | Утверждение истинно во всей исследованной модели | Найдено нарушение | `counterexample` |
| `forbidden_state` | Запрещённое состояние недостижимо | Найдено запрещённое состояние | `counterexample` |
| `reachable` | Найден путь к цели | Полный обход завершён, цель недостижима | `witness` при успехе |
| `deadlock_free` | Блокировки вне допустимого завершения не найдены после полного обхода | Найдена достижимая блокировка | `deadlock_path` |

`TIMEOUT`, `STATE_LIMIT_REACHED`, `MODEL_INVALID` и `ENGINE_ERROR` не подтверждают
недостижимость цели. `witness` не является контрпримером ошибки.

## Генерация и независимость свойств

TLC ищет цель через инвариант, отрицающий её выражение. Нарушение этого
служебного инварианта с трассой означает достижимость, а завершённая проверка
без нарушения — недостижимость. Перебор выполняет TLC, собственного поиска нет.

Если модель содержит `reachable` или `deadlock_free`, `verify` запускает TLC отдельно для каждого
свойства, включая все инварианты. Поиск цели не ограничивается состояниями,
удовлетворяющими другим свойствам: свойства являются утверждениями о поведении,
а не дополнительными guards. Все независимые результаты сохраняются.

`generate_tla` для такой проверки получает модель с одним свойством. Вызов
генератора напрямую со смесью свойств и `reachable`/`deadlock_free` отклоняется: используйте
`verify`, который разделяет запуски и правильно интерпретирует их результаты.
При нескольких свойствах, включая только инварианты/запреты, `verify` также
выполняет независимые проверки: успех или остановка одного свойства не скрывает
идентификаторы и результаты остальных.

## Ответ API

В `verification_result` добавлены поля с пустыми значениями по умолчанию:

- `witness`: путь для модели с единственным достижимым `reachable`;
- `deadlock_path`: путь к выбранной найденной блокировке;
- `property_results`: независимые результаты нескольких свойств, а также одиночных `reachable`/`deadlock_free`.

Каждый элемент `property_results` содержит `property_name`, `property_type`,
`status`, `message`, `counterexample`, `witness`, `deadlock_path`, `related_requirements` и
`statistics`. Путь использует прежний `TraceState`: `number`, `values`,
`transition`, `tlc_label`, `related_requirements`. У первого состояния перехода нет.

Пример части ответа:

```json
{
  "status": "PROPERTY_HOLDS",
  "counterexample": [],
  "property_results": [{
    "property_name": "CanExecute",
    "property_type": "reachable",
    "status": "PROPERTY_HOLDS",
    "witness": [
      {"number": 1, "values": {"ready": false}, "transition": null},
      {"number": 2, "values": {"ready": true}, "transition": "Prepare"}
    ]
  }]
}
```

Пример сокращён: остальные поля имеют стандартные значения. При нескольких
свойствах пути берутся из соответствующего `property_results`, а не смешиваются.
Верхний `counterexample` относится только к выбранному нарушенному свойству;
путь к цели туда никогда не попадает. Старое верхнее поле `AnalysisResult.counterexample`
продолжает дублировать только контрпример и равно `null`, если его нет.

Общий статус имеет приоритет: достоверное `PROPERTY_VIOLATED`, затем
`MODEL_INVALID`, `ENGINE_ERROR`, `TIMEOUT`, `STATE_LIMIT_REACHED`, и только затем
`PROPERTY_HOLDS`. Поэтому установленное нарушение не скрывается сбоем другой
проверки; подробные статусы всегда доступны в `property_results`.
Общий успех означает успех каждого свойства. `violated_property` указывает
первое невыполненное свойство в порядке входной модели.

`MODEL_CHECKER_TIMEOUT_SECONDS` задаёт общий бюджет запусков: следующий TLC
получает оставшееся время. При исчерпании бюджета оставшиеся свойства получают
`TIMEOUT`. Для нескольких запусков общая статистика пуста: статистика каждого
обхода хранится отдельно, суммы не выдаются за число состояний одного графа.

Ссылки на требования наследуются проверяемым свойством и переходами его пути.
На границе Analyst Agent цитаты проверяются по исходному тексту до TLC. Для
прямого вызова Model Checker без текста подтверждение цитат остаётся обязанностью
вызывающего кода (`validate_source_references`).

## Блокировки и допустимое завершение

Свойство без исключений:

```json
{"name":"NoDeadlock","type":"deadlock_free"}
```

Достижимое состояние считается блокировкой, если ни один бизнес-переход
не разрешён. `Created`, `Cancelled`, `Done` не являются допустимым завершением
автоматически. Если требования **явно** разрешают завершение, оно задаётся
предикатом того же DSL в поле `terminal_states`:

```json
{
  "name":"NoDeadlock",
  "type":"deadlock_free",
  "terminal_states":{"eq":[{"var":"phase"},"Done"]}
}
```

`expression` у `deadlock_free` не допускается. У остальных типов по-прежнему
обязательна `expression`, а `terminal_states` запрещено. Предикат завершения
проверяется Validator: неизвестные переменные, неверные типы и выход за домен
отклоняются до TLC. В модели по-прежнему нужен хотя бы один описанный переход;
для тупика достаточно, чтобы все его guards были ложны.

Генератор формирует `BusinessNext` только из `Step_*`, без служебного stutter.
TLC проверяет инвариант `terminal_states \/ ENABLED BusinessNext`. Поэтому
`UNCHANGED vars`, добавленный в `Next` для старых проверок, не маскирует отсутствие
бизнес-переходов. Перебор состояний выполняет TLC; парсер лишь читает его трассу
и проверяет признаки последнего состояния. Определение разрешённости действия
соответствует [ENABLED в документации TLA+](https://www.docs.tlapl.us/using%3Adebugger).

`terminal_states` исключает состояние из проверки блокировки, но не отрезает
выходящие переходы. Из допустимого завершения можно попасть в другую блокировку,
если модель разрешает такой переход. Самопереход, который разрешён бизнес-правилом
и не меняет значения, считается доступным бизнес-переходом. `deadlock_free`
не проверяет прогресс, справедливость или обязательное завершение процесса.

При нарушении `deadlock_path` содержит состояния от initial до первой найденной
блокировки с именами переходов и ссылками. Для блокировки в initial путь состоит
из одного состояния. Поля `counterexample` и `witness` у этого результата пусты;
UI подписывает путь «Путь к блокировке». При смешанной модели все три вида
путей хранятся у соответствующих элементов `property_results` и не подменяют друг друга.
Верхний `deadlock_path` относится к выбранному общему нарушению; если выбрано
другое свойство, пути блокировок доступны у своих `property_results`.

Общий бюджет времени и приоритет статусов остаются прежними. Незавершённая
проверка не подтверждает отсутствие блокировок; неполная трасса или вывод,
не соответствующий заблокированному состоянию, дают `ENGINE_ERROR`.

## Константные свойства

`invariant` и `forbidden_state` допускают булевы литералы и составные константные
выражения. Генератор сохраняет уровень предиката состояния через `TypeOK`:
нарушение уже в initial проверяет настоящий TLC и возвращает одно начальное
состояние с именем свойства. `invariant=true` и `forbidden_state=false` требуют
завершённого обхода; константность не подменяет запуск checker.

## Совместимость с JSON исходной постановки

Старый `POST /api/analyze` и Python `verify` сохраняют существующие формы полей.
Новый `POST /api/v2/analyze` возвращает ту же оболочку анализа с форматом
постановки в `verification_result`; прямой Python-интерфейс
`check_behavior(model, config)` возвращает этот результат без обращения к LLM.
`case_result(result, model)` — чистый адаптер уже выполненной проверки.

| Поле | Старый API | Формат постановки и v2 |
| --- | --- | --- |
| Свойство на входе | `name` | `id` либо `name`; оба допустимы только при равенстве |
| Свойство на выходе модели | `name` | `id` |
| Идентификатор результата | `violated_property` при нарушении | `property_id` при любом статусе одиночного свойства |
| Движок | подразумевается TLC | `engine: "TLC"` |
| Контрпример | массив | `counterexample: {"steps": [...]}` |
| Значения шага | `values` | `state` |
| Номер первого шага | 1 | 0 |
| Сгенерированные состояния | `generated_states` | `states_generated` |
| Глубина | `graph_depth` | `depth` |

Отсутствующий путь представлен `{"steps": []}`; неизвестная статистика — `null`.
Так же преобразуются `witness`, `deadlock_path` и пути каждого `property_results`.
`related_requirements`, тип свойства и названия переходов сохраняются. При
нескольких свойствах каждый элемент `property_results` имеет собственные
`property_id`, `engine`, статус, трассы и статистику. Верхний `property_id`
указывает выбранное нарушение, а при общем успехе нескольких свойств равен
`null`: общего единственного идентификатора нет. При невалидном входе до
получения однозначной модели `property_id` также `null`; `engine` обозначает
настроенный движок и не утверждает, что он запустился.

Пример прямого вызова из `backend/`:

```python
from model_checker import check_behavior

result = check_behavior({
    "variables": [{"name": "ready", "type": "boolean"}],
    "initial": {"ready": False},
    "transitions": [{"name": "Prepare", "guard": True,
                     "effects": [{"set": ["ready", True]}]}],
    "properties": [{"id": "P1", "type": "invariant", "expression": False}],
})
# PROPERTY_VIOLATED, property_id=P1, engine=TLC;
# counterexample.steps[0] = {number: 0, state: {ready: False}, ...}
```

`POST /api/v2/analyze` принимает прежний запрос `{"requirements": "..."}`.
Frontend использует старый endpoint; миграция существующих клиентов не нужна.
Адаптер одинаково сохраняет все шесть статусов, не превращая незавершённость
проверки в успех.

## Предположения интерпретации

Необязательное поле `BehavioralModel.interpretation` не меняет формальную семантику:

```json
{
  "assumptions": ["Начальное ready=false предположено: текст не задаёт initial."],
  "questions": ["Каково начальное значение ready?"],
  "property_rationale": {"CanPrepare": "Пользователь запросил достижимость ready=true."}
}
```

`property_rationale` ссылается на существующие идентификаторы свойств. Поле
опускается при отсутствии; старые JSON и провайдеры сохраняют совместимость.
Списки и причины формирует LLM; checker не подтверждает их полноту/достоверность.
При разделении проверок метаданные интерпретации не передаются в отдельные
TLC-запуски. UI показывает выбранные свойства и метаданные над вкладками,
при отсутствии метаданных — оговорку, затем позволяет явно уточнить текст.

## SANY и предел различных состояний

`TLCConfig.max_states` / `MODEL_CHECKER_MAX_STATES` — необязательный положительный
целый порог (1–2147483647), по умолчанию отключён. Установленный TLC 2.19
(JAR v1.7.4, revision 5a47802) поддерживает `TLCGet("distinct")` из модуля TLC.
Генератор добавляет отдельный служебный инвариант
`MC_StateBudget == (TLCGet("distinct") < N) /\ TypeOK` после пользовательского
свойства. Его нарушение останавливает настоящий TLC и преобразуется только
в `STATE_LIMIT_REACHED`: служебная трасса не становится контрпримером,
`witness` или доказательством недостижимости.

Считаются различные состояния по отпечаткам TLC, включая initial. Это
порог на контрольных точках проверки инвариантов с одним worker (`-workers 1`),
а не лимит сгенерированных кандидатов, памяти или диска. Состояние, на котором
обнаружен порог, уже зарегистрировано TLC; на контрольной модели порог 2
останавливает обход с `distinct_states=2`. Жёсткое ограничение памяти или
всех внутренних выделений до N не заявляется. Срабатывание на границе
возможно даже если непроверенная часть графа мала; повторный запуск с большим
порогом нужен для полного результата. Если пользовательское свойство уже
дало нарушение/путь на том же состоянии, его результат имеет приоритет перед
проверкой служебного инварианта. Порог применяется отдельно к каждому
независимому обходу, timeout остаётся общим для всех свойств.

Перед каждым TLC выполняется отдельный `java -cp <jar> tla2sany.SANY Model.tla`
с тем же временным каталогом и оставшимся бюджетом времени. Для установленного
SANY недостаточно кода выхода: он может вернуть 0 при ошибке. Runner проверяет
диагностику ошибок и завершённую семантическую обработку Model. Невалидный
TLA+ даёт `MODEL_INVALID`; отсутствие Java/JAR/класса, сбой запуска или
неподтверждённый разбор — `ENGINE_ERROR`; превышение времени — `TIMEOUT`.
При timeout Java принудительно завершается и ожидается через `communicate`;
временный каталог удаляется и при ошибках. Автозагрузка инструментов не выполняется.

Выбранный механизм опирается на комментарии `TLC.tla` установленного JAR и
[исходный модуль TLC](https://github.com/tlaplus/tlaplus/blob/v1.7.4/tlatools/org.lamport.tlatools/src/tla2sany/StandardModules/TLC.tla).
SANY и управляемый порог — усиление надёжности, а не новые обязательные
acceptance-сценарии исходной постановки.
